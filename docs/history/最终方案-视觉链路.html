把讨论中定下的每一个岔路口收敛成一条可执行的技术路径。参数已定，剩下的是验证。

Pi 5 · Ubuntu 24.04 · Jazzy 海尔 mini R Pro · 8745HS · 32GB 采集层已于 11-24 修订 yolov8n · PyTorch CPU · 实测 17.7 ms 推理层已于 11-26 实测 链路层 11-26 实测 · 直连 RTT 0.25 ms 网线直连 192.168.10.0/24

一句话结论

Pi 只做"搬运工"，所有智能都放在那台 8 核 Zen4 上，界面用浏览器渲染。

采集层已修订（2026-11-24 实测）。原计划的 v4l2_camera + MJPG 720p30 走不通：该包没有 MJPG 解码路径，启动即 cv_bridge 抛异常 abort；usb_cam 的 raw_mjpeg 则直接 Segmentation fault。最终实测可用的是 usb_cam + YUYV 640×480 @ 19.9fps + republish q80，单帧 60 KB，带宽 1.26 MB/s（10 Mbps）。下面凡是涉及 720p / MJPG / 25 Mbps 的数字都按此折算（推理位置、Web 界面、延迟结构三部分结论不受影响）。

树莓派 5 用 usb_cam 采 UVC 摄像头的 YUYV 原始帧（640×480），经 republish 压成 CompressedImage 走 DDS，通过千兆网线送到海尔主机；主机上的 rclpy 节点解码后交给 ONNX Runtime 跑 yolov8n，检测框坐标随帧下发，由 FastAPI 用 WebSocket 推给浏览器 canvas 前后端分层绘制。

1080p 以上的分辨率全部放弃，H.264 硬编码不存在，CUDA 不可用，虚拟机退出主链路，rosbridge 不参与，Electron 不做。这些否掉的选择在下面"决策记录"里都有理由。

最终架构

五个环节，两个进程边界，一条物理链路。

决策记录

每个岔路口都曾经是开放问题，这里是结论和被否掉的理由。

决策点选定否掉的方案与理由
上位机形态海尔 mini 整机装 Ubuntu 24.04VMware 无 CUDA 通路且 USB 直通影响帧率；WSL2 是「没有第二台机器」时的备选，有物理机就不该绕虚拟化层
摄像头挂哪树莓派 5 的 USB 口挂主机则传输环节消失，项目失去意义；只在测「纯算法基线」时临时插主机
采集节点usb_cam（已修订）原选 v4l2_camera 实测不可用：无 MJPG 解码路径，启动即抛 Unrecognized image encoding [] 并 abort；camera_ros 面向 Pi Camera Module 的 libcamera 通路，对 UVC 反而绕。usb_cam 的 raw_mjpeg 分支在本版会 segfault，只有 yuyv 稳定
像素格式YUYV 640×480（已修订）MJPG 描述符标 30fps 但实测只能到 19.9，且两套驱动都读不了它。YUYV 下 720p 被限到 10fps，640×480 才有 20fps——而 640 正好是 YOLO 的输入宽度，不用缩放
编码复用摄像头输出的 JPEGH.264：Pi 5 无硬件编码器，libx264 软编吃 2~3 核并引入队列延迟，编码器收益为负
传输层ROS2 CompressedImage原始 sensor_msgs/Image 是 660 Mbps，任何网络都扛不住；rosbridge 把二进制转 base64 JSON，帧率会掉到个位数
YOLO 位置主机 CPUPi 本地 CPU 只有 5~8 fps 且与采集抢资源；Hailo-8L 要多花 300~500 元并走模型转换流程，当前无收益
加速后端ONNX Runtime CPUROCm：Radeon 780M 是 gfx1103，不在支持列表，需 hack 且易崩；NPU：8745HS 没有 XDNA（8845HS 才有）
网络网线直连 192.168.10.0/24手机热点约 10~20 Mbps 且抖动大、通常不转发多播、锁屏会断网；直连把「DDS 能不能通」这个最大风险项直接消掉
界面Web（FastAPI + WebSocket + canvas）rviz2 不可定制、渲染偏重，只能当调试工具；PySide6 失去远程访问能力；Electron 双运行时 +300 MB，在「推理在 Python」的架构里不划算
框的叠加位置前端 canvas 画，坐标与原始 JPEG 同包下发后端用 cv2 画框必须把解码后的图重新编码成 JPEG（白费 15~25 ms），且 cv2.putText 不支持中文；两路分开下发必然「框画在错误的帧上」，但装进同一条消息就物理上不可能错位

参数表

可以直接照着写进启动命令和配置文件的数值。

环节组件 / 参数取值与说明
采集pixel_formatyuyv（已修订，原为 MJPG）。配 io_method:=mmap，framerate:=30.0 只是请求值，实际 19.9
采集image_width / height640 / 480（已修订）。720p 在 YUYV 下只有 10fps；640 对 YOLO 的 640 输入零缩放
采集v4l2 控件顺序不能错：exposure_dynamic_framerate=0 → auto_exposure=1 → exposure_time_absolute=30 → gain=63。出厂把「允许降帧率」设成 1，是暗光下掉到 10fps 的元凶
传输QoS全链路 best_effort + depth 1。默认的 reliable/depth5 会在抖动时积压，延迟越跑越大且永不恢复
传输JPEG 质量80。实测 640×480 约 60 KB/帧，19.9fps 合 1.26 MB/s（10 Mbps），千兆链路占 1%
推理模型 / 输入yolov8n · 640×640 · ONNX Runtime，intra_op_num_threads=6 左右（留 2 核给 ROS2 与 Web 服务）
推理取帧策略每轮只取最新一帧。20fps 与 17.7ms 推理正好匹配，正常不积压；但 usb_cam 默认 QoS 是 RELIABLE + depth 100（原始帧 0.92 MB，理论可积压 92 MB），跨机前必须改成 best_effort + depth 1
显示消息格式二进制帧：4 字节 JSON 头长度 + JSON（框、帧号、耗时）+ JPEG 字节
显示渲染底层 canvas 贴图 + 上层透明 canvas 画框；用 requestAnimationFrame 统一绘制，不在消息回调里直接画
网络IP主机 192.168.10.1/24、Pi 192.168.10.2/24，网关留空（填了主机就上不了网，上网走 WiFi）

性能预期

按硬件实测值推算，不是网上抄的数字。误差主要来自 Pi 侧编解码。

阶段耗时说明
Pi usb_cam 采集 + YCbCr→RGB8~12 msYUYV 640×480，0.92 MB/帧，四个 A76 核做色彩空间转换
republish 编码 JPEG q806~10 ms640×480 比 720p 小 2.25 倍，编码开销同步下降；输出 60 KB/帧
DDS 传输（千兆直连）3~8 ms换手机热点这行会变成 15~30 ms 且抖动
主机解码 + 预处理8~12 msimdecode + letterbox 缩放
YOLOv8n 推理17.7 ms8 核 Zen4 走 ONNX Runtime，AVX-512 可用
后处理 + 画框3~6 msNMS + cv2.rectangle
WebSocket + canvas15~25 mscreateImageBitmap 硬件解码 + rAF 绘制
显示刷新8~16 ms60Hz 面板一帧的等待
合计约 100~125 ms。还有一处可选的改进：自己写一个约 40 行的节点，用 V4L2 直接取 MJPG 原始字节塞进 CompressedImage，不解码不编码，能再省 15~20 ms 并降低 Pi 的 CPU。原因是现成的 usb_cam raw_mjpeg 在这版会 segfault，绕开它只能自己写。跑通整条链路之后再考虑，不要提前做。
要知道 120 ms 意味着什么。人眼对「手一动、画面跟着动」的容忍阈值大约在 150 ms 以内，超过就会明显感到"拖"。所以这条链路适合自动检测、录制、远程观察，不适合手动遥控。如果有遥控需求，得回头考虑 WebRTC 或者把推理搬到边缘。

两个还没定的事

1. 检测目标是什么

现在按 COCO 80 类做（person、bottle、cell phone 之类开箱即用）。如果要检测特定物体（比如某个零件、某种手势），就得自己标注 + 训练，那是另一个工程量级，架构不变但周期从一天变成一周。

2. 延迟目标是什么量级

「看着画面做判断」120~160 ms 完全够；「手眼协调地遥控」就得压到 80 ms 以内，那要换 WebRTC 或把推理搬到 Pi 加加速棒。这两个目标对应两套不同的优化路线，越早定越省事。
