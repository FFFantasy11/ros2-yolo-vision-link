树莓派把摄像头跑起来

目标：在没有任何主机参与的情况下，让 /image_raw/compressed 稳定输出 640×480 @ 20fps。已实测跑通，下面是最终确认过的命令和真实数字。

现在就能做 · 约 40 分钟
确认 ROS2 装好了、版本对不对
开一个终端跑。如果输出空白，说明这个终端没加载 ROS2 环境。
echo $ROS_DISTRO
应该看到：jazzy。如果是空白，先跑 source /opt/ros/jazzy/setup.bash 再试一次。
让每个新终端自动加载 ROS2
不做这一步，你每开一个终端都要手动 source 一次，后面开三四个终端会漏。
echo 'source /opt/ros/jazzy/setup.bash' >> ~/.bashrc
source ~/.bashrc
验证：关掉终端重新打开，再跑 echo $ROS_DISTRO，有输出就成功了。
装摄像头相关的三个包
v4l-utils 提供 v4l2-ctl 命令；另外两个提供采集节点和 JPEG 压缩插件。
sudo apt update
sudo apt install -y v4l-utils ros-jazzy-v4l2-camera ros-jazzy-image-transport-plugins
坑：如果提示找不到 ros-jazzy-image-transport-plugins，先确认你加过 ROS2 的 apt 源（装 ROS2 时做过）。也可以单独装 ros-jazzy-compressed-image-transport。
把摄像头插到树莓派上，确认系统认到了
优先插蓝色的 USB 3.0 口。插好后立刻跑下面这条。
ls /dev/video*
应该看到：/dev/video0，可能还有 /dev/video1（那是伴生的元数据节点，不用管）。
什么都没有：换一个 USB 口，线材换短的，别用 USB 延长线或 Hub。还不行就 dmesg | tail -20 看插上瞬间有没有报错。
确认设备名，别认错节点
装了两个以上摄像头设备时，video0 不一定是你的那个。
v4l2-ctl --list-devices
应该看到：一个带摄像头型号名的条目，下面跟着 /dev/video0。记住这个名字，下面用的就是它。
确认格式与设备节点（已完成）
实测结果：设备是 bbdf:0537 camera，采集节点 /dev/video0（sysfs 名字 camera: camera），/dev/video1 是伴生 metadata 节点。板载 video19~37（rpivid / pispbe）全是 ISP 和解码器，跟 USB 摄像头无关，永远不要动。
v4l2-ctl --list-formats-ext -d /dev/video0
实测：MJPG 覆盖 1600×1200 / 1280×1024 / 1280×720 / 800×600 / 640×480；YUYV 在同分辨率下只有 5~30fps，其中 720p 仅 10fps，640×480 才 30fps。
MJPG 标着 30fps，实际跑不到 20fps 以上，所以最后没用它。两个 ROS2 驱动都不行：v4l2_camera 没有 MJPG 解码路径，直接 cv_bridge 抛异常 abort；usb_cam 的 raw_mjpeg 会 Segmentation fault。最终走 YUYV 640×480。
检查供电有没有欠压（这一步能省掉你后面两小时的怀疑）
树莓派 5 用非官方电源时会把 USB 口限流到 600mA，摄像头供电不足会反复重连、掉帧，而且报错很不直观。
vcgencmd get_throttled
必须是：throttled=0x0。出现 0x50000 或 0x50005 说明曾经欠压或降频。
不是 0x0：换官方 27W（5V/5A）电源再继续。用普通 5V/3A 充电头，后面帧率上不去你永远查不到原因。
起采集节点（终端 A，最终采用的命令）
驱动用 usb_cam（sudo apt install -y ros-jazzy-usb-cam），格式用 yuyv，分辨率 640×480。brightness:=0 是因为 usb_cam 启动时会按自己的默认值把亮度改成 50。
ros2 run usb_cam usb_cam_node_exe --ros-args \
  -p video_device:=/dev/video0 \
  -p image_width:=640 -p image_height:=480 \
  -p framerate:=30.0 -p pixel_format:=yuyv \
  -p io_method:=mmap -p brightness:=0
应该看到：Starting 'default_cam' (/dev/video0) at 640x480 via mmap (yuyv) at 30 FPS，然后停住不退出。
标定文件 Unable to open camera calibration file 是正常的，你没标定过，不影响出图。
别传 by-id 路径（/dev/v4l/by-id/...），usb_cam 会拼成 /dev/../../video0 然后报 not a valid device。
另开终端 B，测帧率
这个数字是第一个关键验收点。
ros2 topic hz /image_raw
实测：average rate: 19.87，帧间隔 min 0.048s / max 0.052s，std dev 0.002s。20fps 是这颗模组在 YUYV 下的物理上限，已经排查过曝光、供电、USB 速率、带宽四项，都不足解释。
为什么 20fps 反而是好事：实测单帧推理只有 17.7ms（yolov8n、8 线程、640 输入），20fps 的 50ms 帧间隔里只占三分之一，余量很大，不需要任何跳帧策略。
终端 C：把图压成 JPEG
这条命令会一直占着终端，所以要用第三个终端。-r out:=/image_raw 会让压缩后的话题自动变成 /image_raw/compressed。640×480 的原始帧是 0.92 MB，20fps 就是 18.4 MB/s，必须压完才能跨机。
ros2 run image_transport republish raw compressed --ros-args \
  -p jpeg_quality:=80 \
  -r in:=/image_raw \
  -r out:=/image_raw
应该看到：日志输出后停住不退出。
终端 D：测压缩后的带宽
这是第二个关键验收点，它决定了网络够不够用。
ros2 topic bw /image_raw/compressed
实测：1.26 MB/s，单帧 mean 0.06 MB（约 60 KB）。压缩比 15 倍，折合 10 Mbps。
超过 3 MB/s：JPEG 质量偏高，把 jpeg_quality 降到 70 重启 C。
大于 5 MB/s：可能在传原始帧，检查话题名是不是 /image_raw/compressed。
阶段 1 验收门 · 已通过

实测值（2026-11-24），后面所有调参都以这三个数为基准：

  • ros2 topic hz /image_raw → 19.87（抖动 std 0.002s）
  • ros2 topic bw /image_raw/compressed → 1.26 MB/s，单帧 60 KB
  • 负载 → 待补测：top 那次是在 Ctrl-C 之后跑的，读到的 0.0% CPU 不算数。进程活着时用 top -p $(pgrep -d, -f usb_cam) 看才是真实占用

把主机重装成 Ubuntu 24.04

目标：一台干净的单系统 Ubuntu，装好 ROS2 和 Python 环境。

需要 U 盘 · 约 2 小时（大部分在等安装）
先备份主机上的东西
选"擦除整个磁盘"之后没有任何恢复手段。工作区里已有 ubuntu2404/01-pre-wipe-backup.sh，先看一眼再跑。
确认：这台机器上没有你还需要的文件。有就拷到 U 盘或网盘，别赌。
下载镜像、做启动 U 盘
在你这台 Windows 上做。镜像用 Ubuntu 24.04.3 LTS Desktop，写盘工具用 Rufus 或 balenaEtcher，8GB 以上 U 盘。
注意：一定要选 Desktop 版，不是 Server 版——你后面要在浏览器里看画面。
进 BIOS 关掉 Secure Boot
海尔这台机器开机按 Del 或 F2 进 BIOS。找到 Secure Boot 设为 Disabled，顺便把启动顺序改成 U 盘优先。
不做这步，安装时可能进不去，或者装完核显驱动加载不上。
安装：选"擦除磁盘并安装"+"最小安装"
最小安装会跳过 LibreOffice 那一套，省几个 GB，也少一堆后台服务占内存。
建议勾选："安装第三方软件"（显卡和媒体编解码固件）。AMD 核显虽然有开源驱动，勾了更省事。
首启动：更新系统
装完第一次开机，先更新一轮，避免后面装包时版本冲突。
sudo apt update && sudo apt upgrade -y
sudo apt install -y build-essential git curl vim net-tools
顺便验证核显正常：lspci | grep -i vga 应该能看到 Radeon 780M。
装 ROS2 Jazzy（和树莓派同版本）
你在树莓派上装过一次，流程一样。这里写全，避免你回头翻旧笔记。
sudo apt install -y software-properties-common curl
sudo add-apt-repository universe -y
# GitHub 取 key 在这台机器上会 TLS 中断，改用中科大镜像 + trusted=yes，跳过签名校验
echo "deb [arch=$(dpkg --print-architecture) trusted=yes] https://mirrors.ustc.edu.cn/ros2/ubuntu noble main" \
  | sudo tee /etc/apt/sources.list.d/ros2.list > /dev/null
sudo apt update
sudo apt install -y ros-jazzy-desktop
echo 'source /opt/ros/jazzy/setup.bash' >> ~/.bashrc
验证：重新开一个终端，ros2 topic list 能输出 /parameter_events 和 /rosout。
坑：Ubuntu 24.04 的软件源文件是 /etc/apt/sources.list.d/ubuntu.sources（新格式），不是旧的 sources.list。网上很多换源教程改的是老文件，改完没效果。国内网络慢的话只改新格式那个文件。
建 Python 虚拟环境（必须带 --system-site-packages）
这条参数是关键：不加它，venv 里 import rclpy 会失败，但 ros2 topic list 一切正常，非常迷惑。
sudo apt install -y python3-venv python3-pip
python3 -m venv --system-site-packages ~/venv
echo 'source ~/venv/bin/activate' >> ~/.bashrc
source ~/venv/bin/activate
应该看到：命令行前面多了 (venv)。
装 Python 包
注意 torch 必须装 CPU 版。直接 pip install torch 会下载 2.5GB 的 CUDA 组件，而你没有 NVIDIA 显卡，装了也跑不起来。
# 1) CPU 版 torch：必须用 curl 直下。pip 走同一条链路会被限速到 70 KB/s，curl 能到 10 MB/s
curl -L -o ~/torch-2.15.0+cpu-cp312-cp312-manylinux_2_28_x86_64.whl \
  "https://mirrors.aliyun.com/pytorch-wheels/cpu/torch-2.15.0%2Bcpu-cp312-cp312-manylinux_2_28_x86_64.whl"
curl -L -o ~/torchvision-0.29.1+cpu-cp312-cp312-manylinux_2_28_x86_64.whl \
  "https://mirrors.aliyun.com/pytorch-wheels/cpu/torchvision-0.29.1%2Bcpu-cp312-cp312-manylinux_2_28_x86_64.whl"
pip install ~/torch-2.15.0+cpu-cp312-cp312-manylinux_2_28_x86_64.whl \
            ~/torchvision-0.29.1+cpu-cp312-cp312-manylinux_2_28_x86_64.whl
pip install "setuptools<80"     # pip 会顺手升到 84，colcon 要求 <80
# 2) 其余包体积小，直接 pip
pip install ultralytics "numpy<2" "opencv-python<4.11" fastapi "uvicorn[standard]"
验证：python -c "import rclpy, cv2, torch, ultralytics; print('ok')" 输出 ok。

网线直连，让两台机器互相看见

目标：主机能 ping 通树莓派，而且 ROS2 的话题能跨机收到。

约 30 分钟
插网线
树莓派的网口 ↔ 海尔的 RJ45 口。普通网线就行，两个口都支持自动翻转。主机的 WiFi 不用断，继续用来上网。
主机设静态 IP：192.168.10.1
图形界面最省事：设置 → 网络 → 有线 → 齿轮图标 → IPv4 → 手动 → 地址填 192.168.10.1/24，网关和 DNS 全部留空 → 应用。
网关一定要留空。填了网关，主机的默认路由就跑到这条断网的线上，你会发现自己上不了网，而且是"能 ping 通树莓派但打不开网页"这种很诡异的现象。
图形界面可能把 /24 存成 /0（实测踩到）。现象是网口拿到 169.254.x.x 而不是 192.168.10.1，NetworkManager 认为地址无效直接退回 link-local。这时别在界面上反复改，直接用命令覆盖（连接名用 nmcli -t -f NAME,UUID connection show 查真实 UUID，注意它和 netplan 文件名里那串 UUID 不是一回事）：
sudo nmcli connection modify <UUID> ipv4.method manual ipv4.addresses 192.168.10.1/24 ipv4.gateway "" ipv4.dns ""
sudo nmcli connection up <UUID>
树莓派设静态 IP：192.168.10.2
注意：Ubuntu 版树莓派没有 nmcli，网络由 cloud-init 生成 netplan、再交给 systemd-networkd 管理。直接改 netplan 文件，同时禁用 cloud-init 覆盖，否则重启会被改回去。
sudo cp -a /etc/netplan/50-cloud-init.yaml /etc/netplan/50-cloud-init.yaml.bak
sudo tee /etc/netplan/50-cloud-init.yaml > /dev/null <<"EOF"
network:
  version: 2
  ethernets:
    eth0:
      optional: true
      dhcp4: false
      dhcp6: false
      addresses:
        - 192.168.10.2/24
  wifis:
    wlan0:
      optional: true
      dhcp4: true
      regulatory-domain: "CN"
      access-points:
        "你的热点名":
          auth:
            key-management: "psk"
            password: "你的热点密码"
EOF
# 关键：禁掉 cloud-init 的网络接管，否则重启后配置被覆盖
printf "network: {config: disabled}\n" | sudo tee /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg
sudo chmod 600 /etc/netplan/50-cloud-init.yaml
sudo netplan generate && sudo netplan apply
验证：ip -br addr show eth0 显示 192.168.10.2/24，且 ip route 的 default 仍然走 wlan0。
WiFi 配置必须一起写进这个文件。netplan 是整份替换，只写 eth0 会把原来的 wlan0 配置抹掉；而 netplan apply 过程中 wlan0 还会短暂 DOWN——如果只写了有线，树莓派就彻底失联，只能接显示器救。
wlan0 掉了怎么救：sudo ip link set wlan0 up && sudo systemctl restart systemd-networkd，约 8 秒后回来。
双向 ping 通
两边各跑一次，都要通。
ping -c 3 192.168.10.2
应该看到：3 个包全部收到，延迟小于 1ms。
ping 不通：先 ip -br addr 确认两边地址都设对了，再看网口的指示灯亮不亮。
测 ROS2 能不能跨机发现（这是最容易失败的一步）
树莓派上开一个终端发消息，主机上开一个终端收。
# 树莓派
ros2 topic pub /test std_msgs/String "data: hi" -r 1
# 主机
ros2 topic echo /test
应该看到：主机每秒刷一行 data: hi。
收不到时，先别怀疑网络，按这四步走（实测两个假故障都出在这里）：
① 先 ros2 daemon stop 再重试。ros2 命令行有个常驻守护进程缓存计算图，链路换了、节点重启过，它可能一直在用旧图告诉你"没有这个 topic"。最快的排除法：ros2 topic list --no-daemon，能列出来就是 daemon 的锅；
② 发布端不要用 timeout 20 ros2 topic pub ... 在前台跑，然后再去订阅。它是阻塞的，等你切到另一台机器敲 echo 时，发布端早就退出了。要把发布端放后台常驻：nohup ros2 topic pub -r 2 /test std_msgs/String "{data: hi}" > /tmp/pub.log 2>&1 &，看到日志里 publishing #N 再订阅；
③ 两端 echo $ROS_DOMAIN_ID 是否一致（默认都是空/0），sudo ufw status 排除防火墙；
④ 只有上面都排除了才动单播：两端都 export ROS_STATIC_PEERS=192.168.10.1;192.168.10.2。直连网线下多播是通的，正常情况下不需要单播兜底。
通过之后还有两件事必须做，否则阶段 4 的数字全是假的（实测踩到）：
① 对时。两台机器各自连公网 NTP 时，误差可以到 ±150ms；直连 RTT 只有 0.25ms，所以让主机当 NTP 服务器、Pi 对着主机校时最准（实测偏差降到 85 µs）。主机：apt install chrony，配置加 allow 192.168.10.0/24 与 local stratum 8；Pi：server 192.168.10.1 iburst prefer。
② 强制 DDS 走有线口。默认情况下 DDS 会自己挑接口，实测视频流 100% 跑到了 WiFi 上（有线口一个字节都没走）。用 Fast DDS profile 的 interfaceWhiteList 钉死：两端各写一份 ~/wire.xml，同时保留 SHM 传输（只留 UDPv4 会让本机 614KB 的 raw 图走回环，延迟反而更差），然后 export FASTRTPS_DEFAULT_PROFILES_FILE=$HOME/wire.xml。
阶段 3 验收门 · 已通过

2026-11-26 实测双向通过：主机收到 data: wire-ok，树莓派收到 data: reverse-ok，直连 RTT 0.25 ms（min 0.176 / max 0.308），多播发现正常、未使用任何单播兜底。

这一步过不去，后面全部堵死。所以它必须单独测，不要和出流混在一起。

跨机器把视频流跑通并测量

目标：拿到真实的帧率、带宽、延迟三个数，它们决定后面所有参数。

已完成 · 实测 19.9 fps / 6.1 Mbps / 延迟 p50 3.6 ms
先说结论：阶段 1 的 usb_cam + republish 两级链路不能用，必须换。 它的 /image_raw 发布端是 RELIABLE + KEEP_LAST(100)，单帧 614 KB 的 raw 图乘以 100 就是 61 MB 历史； 下游一旦跟不上，积压只增不减。实测端到端延迟从 950 ms 一路涨到 1177 ms，而且不会自己恢复。 Jazzy 的 usb_cam 没有暴露 publisher QoS 参数，改不了，所以换成一个单节点实现： V4L2 直接取流 → imencode JPEG → 发 CompressedImage，QoS = BEST_EFFORT + depth 1。 换成它之后延迟变成 3.6 ms，降了 260 倍，同时 Pi 上少掉 12 MB/s 的本机 raw 转发、进程从 4 个降到 1 个。
① 准备两样东西：出流节点 + 有线口配置
工作区里 vision/pi/cam_pub.py 和 vision/pi/start_cam_pub.sh 直接拷到树莓派用户目录。另外需要阶段 3 那份 ~/wire.xml（把 DDS 钉死在有线口，否则视频流会跑到 WiFi 上）。
# 从 Windows 拷过去（在 Git Bash 里跑）
scp vision/pi/cam_pub.py vision/pi/start_cam_pub.sh pi@192.168.10.2:~/

# 树莓派上确认没有 CRLF 换行，否则报 $'\r': command not found
sed -i "s/\r$//" ~/cam_pub.py ~/start_cam_pub.sh
chmod +x ~/start_cam_pub.sh
依赖检查：节点的 cv2 和 rclpy 都来自系统 Python（不是 venv）。先 source /opt/ros/jazzy/setup.bash 再 python3 -c "import cv2, rclpy"，不报错就行。
② 启动出流
# 后台跑，日志留在 /tmp/campub.log
nohup bash ~/start_cam_pub.sh > /tmp/campub.log 2>&1 &
sleep 12; tail -5 /tmp/campub.log

只有 10 fps：两个原因，都实测踩过。① MJPG 格式在这个模组上的上限就是 10 fps，必须用 --fourcc YUYV；② CAP_PROP_BUFFERSIZE 设成 1 会让帧率刚好减半（实测 1→10.1 fps、4→19.9 fps、8→19.9 fps），单缓冲下驱动必须等缓冲区回收才能再入队，每两帧才交出一帧。脚本里已经是 4。
画面很暗：节点默认把曝光锁在 10 ms（--exposure 100，单位 100 µs）。没开灯时这是正常的，画面暗不代表参数错。开灯后可以用 --exposure 30（3 ms）换取更短的采集时刻。注意曝光必须在 open 之后设——打开设备会把控件恢复成自动曝光，暗光下自动曝光会拉到 100 ms，帧率直接掉一半。脚本已经处理了顺序。

让 YOLO 出第一个框

目标：用 COCO 预训练模型在画面上画出检测框，并测出单帧推理耗时。

约 1 小时 · 到时我给完整脚本
先用一张静态图确认模型能用
不要一上来就接视频流。先确认模型本身跑得动，问题范围就缩小到"链路"和"模型"两个独立部分。
必须用 ~/venv/bin/python3，不能用系统 python3。ultralytics 和 torch 都装在 venv 里，系统 Python 里没有，直接 python3 -c "import ultralytics" 会报 ModuleNotFoundError。而跑 ROS 节点用系统 Python 更方便，所以这台机器上两种 Python 混着用，每次都要想清楚是哪一种。
~/venv/bin/python3 -c "
from ultralytics import YOLO
m = YOLO('yolov8n.pt')
r = m(0, save=True)      # 0 = 摄像头；改成图片路径也行
print('detected:', len(r[0].boxes))
"
应该看到：下载 6 MB 的 yolov8n.pt（只需一次），然后打印出检测到的目标数量。结果图存在 runs/detect/predict/ 下。
单独测纯推理耗时
这个数决定了你的实际帧率上限。CPU 推理要做多次取平均，第一次总是特别慢（预热）。
~/venv/bin/python3 -c "
import time, numpy as np, torch
from ultralytics import YOLO
torch.set_num_threads(8)
m = YOLO('yolov8n.pt')
x = np.random.randint(0,255,(480,640,3),dtype=np.uint8)
for _ in range(3): m.predict(x, verbose=False)
t=time.perf_counter()
for _ in range(20): m.predict(x, verbose=False)
print(f'{(time.perf_counter()-t)/20*1000:.1f} ms/帧')
"
本机实测：17.7 ms（中位；最快 17.1 / 最慢 19.8，8 线程、640 输入、随机权重、预热 3 次后取 12 次中位）。纯 forward 上限约 56 fps，20 fps 的 50 ms 帧间隔只占三分之一。如果明显高于 25 ms，检查 torch.set_num_threads(8) 是否设了；这颗 8745HS 是 8 核 16 线程，不设的话 torch 可能只用 1 个核。
接上视频流出框
用 vision/host/yolo_view.py。先不做网页——窗口或存图里能一眼看出"框有没有画在正确的位置"，而网页里还要多怀疑一层前端。
# 方式一：存带框图（不需要图形界面，远程也能验证）
export FASTRTPS_DEFAULT_PROFILES_FILE=$HOME/wire.xml
~/venv/bin/python3 ~/yolo_view.py --save /tmp/yolo --save-every 20 --seconds 20

# 方式二：在主机屏幕前看本地窗口
DISPLAY=:0 ~/venv/bin/python3 ~/yolo_view.py --display

# 只检测人（COCO 里 person 是 0）
~/venv/bin/python3 ~/yolo_view.py --display --classes 0 --conf 0.4
实测输出：19.8~20.0 fps ｜ 推理中位 16.7~19.6 ms ｜ 延迟 p50 24.9~37.2 ms ｜ 左下角叠了一行 fps | infer | lat | obj（分别是渲染帧率、推理毫秒、端到端延迟、本帧目标数）。
第一帧的指标不用当真。刚启动那帧会显示 infer 900+ ms、lat 900+ ms——那是模型首次前向的预热开销，加上该帧时间戳已经很旧。从第 3 帧起就稳定在 20 ms 内了。
单帧大小会随环境光变化：深夜没开灯约 37 KB，白天光线足时约 55 KB（细节多、压缩率低），对应带宽 6 Mbps → 8.6 Mbps。这是正常现象，不是参数变了。
脚本的关键设计：回调只存最新帧，主循环才推理。如果直接在订阅回调里跑 YOLO，executor 会被占住 20 ms，DDS 那边新帧继续到，处理慢于到达就开始积压——就是阶段 4 那个 956 ms 的成因。现在回调只做"覆盖 self.latest 并立刻返回"，慢就丢旧帧，物理上排不了队。
别用 cv2.putText 写中文类别名，它只支持 ASCII，中文会变成一串问号。脚本直接用 res[0].plot()，框、颜色、标签、置信度都由 ultralytics 画好，最省事也最不容易错位。
阶段 5 验收门 · 已通过

2026-11-26 实测：19.8 fps ｜ 推理 17.6 ms ｜ 端到端延迟 p50 35.5 ms ｜ 143 帧检出 170 个目标。框位置核对过：person 0.75 的框上沿在头顶上方一点、左右边界贴着两肩外缘，没有偏移；不同时刻抓的帧里框的位置和大小都在变，说明是实时跟随而不是画死的。

模型是 80 类 COCO（yolov8n.pt，6.3 MB）。至此"链路 → 推理 → 画框"整条都验证过了，阶段 6 只需要把同样的三步搬进 WebSocket。

换成网页界面

目标：浏览器打开一个地址就能看画面和检测结果，同一个网络里任何设备都能看。

已完成 · 实测 19.9 fps / 推理 24.2 ms / 延迟 24.6 ms
核心设计：框不在服务端画，而是发原图 + 框坐标，让浏览器画。 服务端把摄像头原始的 JPEG 字节和检测框 JSON 装进同一条 WebSocket 二进制消息，前端拿到后先贴图、再按同一帧的坐标画框。 三个好处：① 省掉服务端一次「编码带框图」的开销（15~25 ms）；② 框是矢量的，缩放不糊，标签能用任意字体；③ 框和画面来自同一条消息，物理上不可能错位——这是选这个协议的核心理由，不是顺手为之。
① 两个文件放到位
后端 vision/host/web_server.py，前端 vision/host/web/index.html。前端必须放在后端同级目录的 web/ 下，服务按这个相对路径找它。
# 从 Windows 拷到主机（在 Git Bash 里跑）

ssh <用户>@<主机IP> 'mkdir -p ~/web'
scp vision/host/web/index.html <用户>@<主机IP>:~/web/
目录结构：~/web_server.py 与 ~/web/index.html 必须并存，位置错一个就会打开页面 404。
② 先补一条订阅依赖，再启动服务
FastAPI 处理 WebSocket 要 websockets 或 wsproto。装 uvicorn 时用 uvicorn[standard] 就已经含了；如果只装了裸 uvicorn，启动会报 No supported WebSocket library detected。
~/venv/bin/pip install "uvicorn[standard]"

# 启动（后台，日志在 /tmp/web.log）

sleep 10; tail -5 /tmp/web.log
应该看到：服务启动：http://0.0.0.0:8000。用 curl http://<主机IP>:8000/health 应返回 {"ok":true,"frames":N,"ver":N}，frames 在持续增长说明 DDS 收得到帧。
frames 一直是 0：DDS 没通或话题名不对。先确认 FASTRTPS_DEFAULT_PROFILES_FILE 已设，再 ros2 topic list 看 /image_raw/compressed 在不在。服务本身没崩，不要重启它。
