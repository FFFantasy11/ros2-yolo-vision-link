# 设计说明

## 一、链路总览

```
┌─────────────── 树莓派 Pi 5 (Ubuntu 24.04.5 arm64) ───────────────┐
│  USB 摄像头 /dev/video0                                          │
│      │ V4L2 (YUYV 640x480@20)                                    │
│      ▼                                                           │
│  vision_cam  [C++]  ── JPEG 编码 ──┐                             │
└────────────────────────────────────┼─────────────────────────────┘
                                     │ 有线千兆 192.168.10.0/24
                                     │ Fast DDS（wire.xml 限定网卡）
                                     ▼
┌─────────────── 海尔主机 (Ubuntu 24.04.5 x86_64) ─────────────────┐
│  vision_detect [Python]                                          │
│      订阅 CompressedImage (BEST_EFFORT, depth 1)                 │
│      → YOLOv8n 推理 (ultralytics/torch, ~17ms)                   │
│      → HTTP + WebSocket :8000                                    │
│  vision_probe  [C++]  只统计，不推理（验收/排障用）              │
└──────────────────────────────────────┬───────────────────────────┘
                                       │ WebSocket 二进制帧
                                       ▼
                              浏览器 canvas 绘制
```

## 二、三个节点各自的责任

| 节点 | 运行位置 | 语言 | 职责 | 不做的事 |
|---|---|---|---|---|
| `vision_cam` | 树莓派 | C++ | 取流、编码 JPEG、发布 `/image_raw/compressed` | 不推理、不做任何图像处理 |
| `vision_detect` | 主机 | Python | 订阅、推理、推流网页 | 不在回调里推理 |
| `vision_probe` | 主机 | C++ | 测帧率/带宽/抖动/延迟 | 不推理、不显示 |

## 三、为什么是「C++ + Python」混合，而不是全 C++

原始需求是把节点全部用 C++ 重写。实际做下来，采集与探针顺利迁移，推理节点不行，
原因是硬性技术限制，不是工作量问题：

1. **OpenCV 4.6 的 dnn 模块跑不了 YOLOv8**。Ubuntu 24.04 源里的 `libopencv-dev`
   就是 4.6.0，解析 ONNX 时在检测头 `model.22/Add` 处断言失败
   （`blob_0.size == blob_1.size`，parseBias）；
   用 onnxsim 把 Conv+Add 融成单个 Conv 后，解析通过，但 `forward()` 又抛
   `start <= shape.size()` 的形状断言。两条路都堵死。
2. **ONNX Runtime 的 C++ 开发包拿不到**。PyPI 镜像可达，但 onnxruntime 的 wheel
   里只有一个 `libonnxruntime.so`，没有头文件；GitHub Release 直连和 ghproxy
   都是 404，离线环境无法获取 C++ 头文件。
3. 即便强行凑通，也要引入 torch（2GB 依赖）或 ORT 的版本匹配问题，把一条已经
   稳定跑通的链路变成维护负担 —— 违反「保持原有功能不变」的前提。

因此最终划分：**能用 C++ 拿到收益的（Pi 端采集、链路探针）用 C++，依赖深度学习
框架的推理节点保留 Python**。这符合「不得不用 Python 的就没必要改成 C++」。

C++ 采集节点带来的实际收益：Pi 上省掉 Python 解释器与 numpy 中转
（systemd 统计常驻 22.9MB）；控件改用 `VIDIOC_S_CTRL` 直接写，启动时不再
fork 五个 `v4l2-ctl` 子进程，还能回读校验驱动是否截断；取流循环由摄像头
节奏驱动，去掉了 Python 版 1/fps 定时器的节拍开销（链路延迟从 p50 3.6ms
降到亚毫秒级）。

## 四、关键设计取舍（每条都是实测换来的）

### 1. QoS：BEST_EFFORT + KEEP_LAST(1)

旧方案 `usb_cam` 发布 `/image_raw` 用 RELIABLE + depth 100。640x480 YUYV 一帧
600KB，100 帧历史就是 61MB；下游一旦跟不上，积压只增不减，
端到端延迟从 950ms 一路涨到 1177ms。

实时视频的正确取舍是**宁可丢帧，绝不排队**：丢掉的旧帧对"看当前画面"毫无价值，
而排队的每一帧都在增加延迟。发布端和订阅端都必须设成 BEST_EFFORT + depth 1，
只设一端没用。

### 2. 采集用 YUYV 而不是 MJPG

这个模组 MJPG 上限只有 10fps，YUYV 才能到 20fps。

### 3. `buffers` 必须大于 1

单缓冲下驱动必须等缓冲区回收才能重新入队，每两帧才能交出一帧：
实测 `buffers=1 → 10.1fps`、`4 → 19.9fps`、`8 → 19.9fps`。取 4。

### 4. 控件必须在 `open()` 之后锁死，且顺序固定

打开设备会把控件恢复成驱动默认值，其中 `exposure_dynamic_framerate` 默认允许
自动降帧 —— 暗光下自动曝光把积分时间拉到 100ms，帧率立刻掉到 10fps。
所以顺序必须是：关动态降帧 → 切手动曝光 → 写曝光时间 → 写增益 → 写亮度。
`vision_cam` 用 `VIDIOC_S_CTRL` 直接写（不再 fork `v4l2-ctl`），写完还会回读校验，
驱动截断时会打警告。

### 5. 推理只做一次，所有客户端共享

推理 17ms/帧。若每个浏览器连接独立推理，3 个人看就是 3 倍 CPU。
`vision_detect` 用「单 worker 更新共享槽 + 所有客户端读同一份 + 版本号变更才推送」
的广播模型，N 个客户端只增加网络发送开销。

### 6. 回调和推理分离

ROS 回调里只做 `imdecode` 和覆盖「最新帧」槽，立刻返回；推理在独立线程。
回调里跑推理会把 executor 占住，消息开始堆积 —— 这和旧方案的积压是同一种错误。

### 7. 二进制协议：`[4B 长度][JSON 头][JPEG]`

```
offset 0  : uint32 LE   头长度 N
offset 4  : N 字节      UTF-8 JSON: {"w","h","dets":[{"x1","y1","x2","y2","cls","name","conf"}],"fps","infer_ms","lat_ms","n"}
offset 4+N: JPEG 字节
```

服务端发**原图**，框以矢量坐标随同一帧下发，前端 canvas 画框。
好处：框和画面物理上不可能错位（同一帧同一份数据）、框是矢量不糊、
不用服务端改像素。

### 8. DDS 限定有线网卡（wire.xml）

两台机器同时开着 WiFi 和网线时，Fast DDS 默认会把发现包和视频流发到 WiFi。
用 `interfaceWhiteList` 把 UDPv4 锁到有线口后，帧间隔 p99 从 210ms 回到 52ms。
两端各自填自己有线口的 IP（主机 `192.168.10.1`、Pi `192.168.10.2`），混用会表现为
"能 ping 通但收不到画面"。

### 9. 时钟同步

`lat_ms` = 主机收帧时刻 − Pi 打时间戳时刻，两机时钟不同步时这个数字完全不可信。
主机当 NTP 服务器（`allow 192.168.10.0/24` + `local stratum 8`），Pi 指向主机，
对时后偏差 -85µs 量级。

### 10. 线程布局（vision_detect）

| 线程 | 职责 |
|---|---|
| ROS 执行器 | 只订阅、只覆盖最新帧 |
| 推理 worker | 取帧 → 推理 → 编码 → 写共享槽 |
| uvicorn 主线程 | 每 8ms 轮询版本号，有新版就推给该客户端 |

## 五、工作空间组织

遵循 ROS 2 社区惯例：

```
ros2_ws/
└── src/
    ├── vision_cam/        ament_cmake，C++ 节点 + config/ + launch/
    ├── vision_detect/     ament_python，Python 节点 + config/ + launch/ + web/
    └── vision_probe/      ament_cmake，C++ 探针
```

约定：

- 可执行文件一律 `install(TARGETS ... DESTINATION lib/${PROJECT_NAME})`
- 运行期资源（yaml、前端页面、launch）装到 `share/${PROJECT_NAME}/`
- 节点参数全部走 ROS 参数 + yaml，改参数不重新编译
- `build/ install/ log/` 属于产物，不进备份的源码部分（可执行文件单独归档）
